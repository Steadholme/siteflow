# SiteFlow Production Distance Matrix

Date: 2026-06-08

SiteFlow is production-hardened only for a narrow trusted single-host or controlled staging profile. It is not full production-ready. This matrix separates current capability from the evidence still needed in a real target environment.

| Area | Current capability | Supported scope today | Full production blocker | Required real-environment evidence |

## Hard blockers for full production

- Real Postgres multi-worker queue and migration rehearsal.
- Real restore drill against disposable Postgres and artifact targets.
- Off-host backup automation beyond externally scheduled `backup:automation`: real target object-storage execution evidence, full provider-side security/retention audit beyond sampled object proof, applied recurring schedule evidence, alert delivery proof, recurring retention proof, and SiteFlow-managed recurring restore-drill automation.
- Real release-gate promotion evidence from the protected target GitHub repository for the exact release commit.
- Passing combined release evidence bundle for the exact release commit, including source provider, operator access, non-session credential, ingress, and upgrade/rollback drill evidence.
- Release source cleanup is complete in commit `54a7243`, but a reviewed release-readiness commit is still required: production hardening files are still mixed with dirty/untracked WIP and cannot be promoted until explicitly staged, reviewed, and committed.
- Target validation for `docker-compose.production.yml` is still missing because local static checks are not a substitute for `docker compose config`, startup, readiness, and restart evidence on the target host.
- Non-dry-run Docker build runner rehearsal evidence in the target profile.
- Metrics scrape collector, backup automation run-record/history support, starter provisioning artifacts, release/target binding, and apply-proof asset hash checks exist, but automated target-stack application/provider verification, alert delivery, log shipping, and incident ownership still need target-environment proof.
- Target ingress evidence must prove API direct-port blocking, forwarded-header cleanup, final-hop proxy source policy, and shared/edge API `429` behavior for the actual topology.
- Stronger build isolation beyond the trusted single-host Docker socket profile.
- Full operator login/session lifecycle beyond the current API-level session create/rotate/revoke, project-scope, CSRF-header, actor-attribution, and emergency-cutoff MVP.
- Real non-session credential rotation execution remains operator-managed; Wave 043 only gates evidence and blocks automatic-rotation claims.
- Upgrade and rollback rehearsal for API, worker, schema, and artifacts remains required, but now has a first-class evidence gate.

## Trusted single-host and staging-only capabilities

- Docker socket worker profile: trusted single-host only.
- Docker source-build runner: acceptable for trusted source builds and staging, not for untrusted multi-tenant workloads.
- Local artifact storage: acceptable for single-host/staging, not a complete external object storage production path.
- Committed production Compose profile: useful as an audited single-host baseline, not a replacement for target host validation or a high-availability deployment design.
- Process-local metrics and in-process rate limiting: acceptable for single-instance operation, not a multi-instance production control plane. Installer-managed Nginx now adds a single-host edge `/api` limiter, and trusted proxy hardening protects forwarded header interpretation, but multi-instance or multi-ingress deployments still need equivalent shared or edge rate limiting evidence.
- Manual release plus externally scheduled backup/restore automation workflows: acceptable for controlled staging; full production needs scheduler ownership, alerting, and object-storage/provider-backed backup paths with KMS and retention proof.

## Evidence that must come from real environments

- Protected GitHub branch and exact commit CI check-run evidence.
- Combined release evidence bundle tying the exact commit to promotion, Docker build rehearsal, source provider, Postgres, backup, observability, operator access, non-session credential, ingress, and upgrade/rollback evidence.
- Source provider evidence from the target provider proving exact checkout, signed webhook delivery, credential hygiene, deploy-key/host-key policy, and release provenance.
- Disposable Postgres restore-drill evidence using a real backup.
- Disposable artifact restore evidence with checksum and file-count verification.
- Concurrent queue and migration rehearsal against real Postgres.
- Production Compose validation, startup, restart, and readiness evidence from the actual target host.
- Readiness probe integration in the actual load balancer/orchestrator.
- Release-bound metrics scrape, backup automation gauges, apply-proof asset hashes, and alert delivery through the actual observability stack.
- Log shipping and retention proof from the actual runtime.
- TLS/DNS/preview route verification for the actual domain.
